# Модуль household 

(Сімейні витрати) — це центральний функціональний блок вашого проєкту, розроблений за архітектурним патерном «Модульний моноліт» (Modular Monolith).

Його головна бізнес-мета — забезпечити спільний облік витрат, покупок та фінансів усередині сім'ї або групи людей (наприклад, співмешканців), з чітким розмежуванням прав доступу.

Нижче наведено детальний опис структури, сутностей та логіки роботи цього модуля, розбитий по шарах.

# 1. Які бізнес-задачі вирішує модуль?
Груповий облік: Користувачі об'єднуються в групи (сім'ї), де кожен має свою роль (Власник, Редактор, Глядач).

Прив'язка до об'єктів (Активів): Витрати не йдуть «у повітря» — вони прив'язуються до конкретного об'єкта спільної власності (будинок, машина, дача тощо).

Атомарне внесення чеків: Можливість зберегти за один клік шапку чека (де, коли і по якому активу купували) разом із деталізованим списком товарів, їхньої кількості та цін.

Історична точність (Зліпки даних): Якщо товар у довіднику перейменують через рік, історія витрат у чеку не зміниться, завдяки архітектурному збереженню текстових зліпків.

# 2. Структура Даних (Які моделі задіяні)
Модуль складається з 7 основних взаємопов'язаних таблиць у базі даних:

## А. Керування доступом
Group (Група): Об'єднання користувачів. Наприклад, група «Наша сім'я». Вона володіє активами та чеками.

GroupMember (Учасник групи): Проміжна таблиця (M2M) між групою та користувачем Django (auth.User). Вона визначає роль:

creator (Власник) — може все, включаючи видалення групи та чеків.

editor (Редактор) — може вносити витрати, додавати товари й магазини.

viewer (Глядач) — може тільки дивитися звіти та історію.

## Б. Об'єкти та місця
Asset (Актив): Конкретна сутність, на яку йдуть гроші (наприклад, автомобіль Tesla або Квартира в Києві). Кожен актив обов'язково належить одній групі.

Market (Магазин): Глобальний довідник місць покупок (наприклад, АТБ, Сильпо, Shell). Має гнучку прив'язку до гео-локації (країна/регіон/місто) через зовнішні контракти API.

## В. Товари та Чеки
Category (Категорія): Деревоподібний довідник категорій товарів (наприклад, Продукти → Напої → Алкоголь). Керується глобально через адмінку.

Product (Товар): Конкретне найменування (Хліб Бородинський, Молоко 2%). Має одиницю виміру (шт, кг, л) та прив'язку до категорії.

Purchase (Чек / Покупка): Шапка документа. Містить дату, текстову нотатку, посилання на Asset, Market та користувача, який його створив.

PurchaseItem (Рядок чека): Складова частина чека. Зв'язує чек із конкретним Product, фіксує кількість, ціну за одиницю та зберігає product_name_snapshot (текстове ім'я товару на момент покупки).

# 3. Архітектурні шари модуля (Clean Architecture / CQRS)
Модуль спроєктований так, щоб логіка бази даних, бізнес-правила та API були повністю ізольовані один від одного. Запит з фронтенду проходить суворий ланцюжок:

1. Шар API (Views & Serializers)
Приймає HTTP-запити від Vue.js.

Використовує чисті ViewSet (без каші з автоматичних методів ModelViewSet).

Серіалізатори тут займаються тільки валідацією структури JSON та форматуванням відповідей.

2. Шар DTO (Data Transfer Objects)
Чисті Python-класи (@dataclass).

Трансформують валідовані дані з DRF у строго типізовані об'єкти (використовуючи сучасні стандарти, такі як Sequence для списків). Они захищають бізнес-логіку від прив'язки до DRF.

3. Шар Сервісів (Business Logic)
Серце додатка. Тут перевіряються бізнес-правила (наприклад: «Чи має право цей користувач писати в цей Актив?»).

Взаємодіє із зовнішніми модулями (наприклад, перевіряє існування міст через контракт GeoConfig.service).

4. Шар Репозиторіїв та Селекторів (CQRS - Розділення Читання/Запису)
Selectors (Читання): Виконують чисті SQL-запити для вибірки (AssetSelector, ProductSelector). Вони оптимізують запити (використовують select_related, prefetch_related), щоб уникнути проблеми N+1.

Repositories (Запис): Відповідають за створення та зміну об'єктів. Наприклад, PurchaseRepo використовує transaction.atomic() для безпеки та bulk_create для швидкого масового збереження рядків чека.

5. Контейнер залежностей (apps.py)
При старті додатка Django, у методі ready(), всі шари склеюються (Dependency Injection). Сервіси отримують свої репозиторії та селектори, формуючи готові синглтони (наприклад, HouseholdConfig.purchase_service).

4. Переваги такої реалізації
Тестованість: Ви можете легко протестувати сервіси та репозиторії звичайними юніт-тестами без запуску HTTP-сервера чи DRF.

Безпека даних: Завдяки транзакціям у репозиторіях, база даних ніколи не залишиться у «зламаному» стані (не з'являться чеки без товарів).

Незалежність фронтенду: API віддає чисті структуровані JSON-дані, які ідеально лягають на реактивні компоненти вашого Vue.js / Tailwind v4 інтерфейсу.
